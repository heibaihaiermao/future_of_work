# Task

You are helping build a structured repository of job requirements extracted from Statistics Canada EC job posters.

The input consists of:

1. An existing requirement repository (which may initially be empty).
2. One job poster already parsed into JSON.

Your task is to:

* extract all meaningful requirements from the job poster;
* organize them into standardized categories;
* reuse existing requirement labels whenever they describe the same requirement;
* create new labels only when no existing label accurately represents the requirement;
* update the repository accordingly.

---

# Categories

Extract requirements into the following categories only.

* Education
* Experience
* Knowledge
* Technical Skills
* Competencies
* Abilities
* Assets

If a requirement clearly belongs in one category, place it there.

Do not duplicate the same requirement across multiple categories unless the job posting explicitly lists it in multiple categories.

---

# Requirement Labels

Each requirement must have a unique, reusable label.

Examples:

* Python Programming
* R Programming
* SAS Programming
* Statistical Analysis
* Survey Methodology
* Data Visualization
* Machine Learning
* Project Management
* Oral Communication
* Written Communication
* Thinking Things Through
* Working Effectively With Others

These labels should be:

* concise;
* reusable across job posters;
* independent of wording;
* stable over time.

Do NOT create labels that are specific to a single poster unless necessary.

---

# Repository Usage

An existing repository will be provided.

For every extracted requirement:

1. Search the repository.

2. If an existing label represents the same requirement, reuse that label exactly.

3. If no existing label exists, create a new one.

4. Add the original wording from this job poster under that label.

Never create duplicate labels for the same concept.

For example, these should map to the same label:

* Ability to communicate orally
* Ability to communicate effectively orally
* Oral communication skills

↓

Oral Communication

---

# Preserve Original Wording

Every label must record every wording encountered.

Example:

Repository:

```json
{
  "Oral Communication": {
    "category": "Abilities",
    "wordings": [
      "Ability to communicate orally",
      "Ability to communicate effectively orally",
      "Strong oral communication skills"
    ]
  }
}
```

Never discard original wording.

---

# Output Format

Return a JSON object with two top-level fields.

```json
{
    "position": {
        "EC-05": {
            "Senior Analyst": {
                "Education": [],
                "Experience": [],
                "Knowledge": [],
                "Technical Skills": [],
                "Competencies": [],
                "Abilities": [],
                "Assets": []
            }
        }
    },

    "repository": {

        "Oral Communication": {

            "category": "Abilities",

            "wordings": [
                "Ability to communicate orally",
                "Ability to communicate effectively orally"
            ]
        },

        "Python Programming": {

            "category": "Technical Skills",

            "wordings": [
                "Python",
                "Programming in Python",
                "Experience using Python"
            ]
        }
    }
}
```

---

# Extraction Rules

* Preserve all explicit education requirements.

* Preserve all explicit experience requirements.

* Preserve all named competencies.

* Preserve all abilities.

* Preserve all asset qualifications.

* Preserve technical skills and software separately whenever practical.

* Ignore administrative text such as:

  * Area of Selection
  * Security Clearance
  * Language Profile
  * Conditions of Employment
  * Operational Requirements
  * Definitions of "recent" or "significant" experience

unless they contain an actual skill or competency.

---

# Canonicalization

Normalize obvious wording differences.

Examples:

* communicate effectively orally
* oral communication
* ability to communicate orally

↓

Oral Communication

Likewise:

* R
* R programming
* programming using R

↓

R Programming

However, do not merge distinct concepts merely because they are related.

For example:

* Statistical Analysis
* Data Analysis

should remain separate unless the repository already treats them as the same requirement.

---

# General Principles

* Prefer reusing existing labels over creating new ones.
* Keep labels short and human-readable.
* Preserve every original wording.
* Return valid JSON only.
* Do not include explanations or markdown.
